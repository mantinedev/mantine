# Controllers and stores

Some Mantine components can be driven with a hook. Call `use<Component>` in your component,
get back an object with actions and queries, and pass it to the component with a prop. There are
two kinds of these objects:

- A controller is passed with the `controller` prop. It adds actions and queries to a component
  that you use as is, for example `expandAll()` on `Accordion` or `next()` on `Stepper`.
- A store is passed with the `store` prop. It is a building block for your own component:
  `Select`, `MultiSelect` and `Autocomplete` are built on top of `Combobox` with `useCombobox`,
  and `useSelect` lets you build your own component on top of `Select` in the same way.

Both are optional. Every component works without them with `value`, `defaultValue` and `onChange`
props (or the component's own spelling, for example `opened`/`onChange`), see
[Controlled vs Uncontrolled](/guides/controlled-vs-uncontrolled).

## Controllers

A controller owns the component state and exposes actions and queries on it. Create it with the
hook, pass the same state options that the component accepts as props, and pass the result to the
component with the `controller` prop:

```tsx
import { Accordion, Button, useAccordion } from '@mantine/core';

function Demo() {
  const controller = useAccordion({ multiple: true, defaultValue: ['first'] });

  return (
    <>
      <Button onClick={controller.expandAll}>Expand all</Button>
      <Button onClick={controller.collapseAll}>Collapse all</Button>

      <Accordion controller={controller}>
        <Accordion.Item value="first">{/* ... */}</Accordion.Item>
        <Accordion.Item value="second">{/* ... */}</Accordion.Item>
      </Accordion>
    </>
  );
}
```

Use a controller when props are not enough:

- To call an action that depends on state the component owns internally. `expandAll()` needs the
  list of mounted `Accordion.Item` components, which you cannot reconstruct from outside.
- To drive the component from outside its subtree. The hook can be called in a parent, a context
  provider or a layout, and its actions passed to a toolbar or a keyboard shortcut handler.
- To read state that `onChange` does not report, for example `isExpanded(item)` or `getItems()`.

Each component documents the actions and queries of its controller on its own page, see the
[list of components](#components-with-controllers) below.

## Stores

A store is created and passed the same way, with a `use<Component>` hook and the `store` prop, but
it has a different purpose. A controller drives a component that you use as is. A store is a base
for your own component with its own props and behavior. For example, `useSelect` reuses the value,
search and dropdown handling of `Select` to build a select that offers to create an option from the
search text:

```tsx
import { Select, useSelect } from '@mantine/core';

interface CreatableSelectProps {
  data: string[];
  onCreate: (item: string) => void;
}

function CreatableSelect({ data, onCreate }: CreatableSelectProps) {
  const store = useSelect({
    onChange: (item) => {
      if (item !== null && !data.includes(item)) {
        onCreate(item);
      }
    },
  });

  const search = store.getSearch().trim();
  const canCreate = search !== '' && !data.includes(search);

  return <Select store={store} searchable data={canCreate ? [...data, search] : data} />;
}
```

`Combobox`, `Tree` and `DataGrid` are building blocks by design, so they work with a store as
well, see the [list of components](#components-with-stores) below.

## Controller and props

When the `controller` prop is set, the controller owns the state and the state props of the
component are ignored. Pass them to the hook instead:

```tsx
import { Accordion, useAccordion } from '@mantine/core';

// ✅ State options go to the hook
const controller = useAccordion({ multiple: true, defaultValue: ['first'] });
<Accordion controller={controller} />;

// ❌ multiple and defaultValue are ignored, the controller already owns them
const controller = useAccordion();
<Accordion controller={controller} multiple defaultValue={['first']} />;
```

The `controller` prop description in the props table of each component lists the props it
replaces. Styling and rendering props, for example `size`, `variant`, `classNames` and children,
are never affected, and adding a controller never removes or renames a prop, so it is safe to adopt
one in existing code. The same rules apply to the `store` prop.

## Usage with forms

`form.getInputProps('field')` from [@mantine/form](/form/use-form) returns `value`, `onChange`,
`error`, `onFocus` and `onBlur` (`defaultValue` instead of `value` in
[uncontrolled mode](/form/uncontrolled)), and other form libraries provide a similar set of props.
These props bind to the state props of the component, so how they combine with a controller depends
on whether the controller owns the value.

Most controllers do not own the value. `useDateInput`, `useDatePickerInput`, `useCalendar` and the
other `@mantine/dates` controllers own the displayed date, level and dropdown, while the selected
value stays on the component. For these components, spread `form.getInputProps()` on the component
and pass the controller next to it, the two do not overlap:

```tsx
import { DateInput, useDateInput } from '@mantine/dates';
import { useForm } from '@mantine/form';

function Demo() {
  const form = useForm({ mode: 'uncontrolled', initialValues: { date: null } });
  const controller = useDateInput();

  return (
    <DateInput
      controller={controller}
      key={form.key('date')}
      {...form.getInputProps('date')}
    />
  );
}
```

Three controllers own the value, because the component keeps entry state that `value` cannot
express: `usePinInput` (one character per input), `useTimePicker` (hours, minutes, seconds and am/pm
fields) and `useMaskedDateInput` (day, month, year and time fields). When one of them is passed, the
`value`, `defaultValue` and `onChange` props of the component are ignored, so `form.getInputProps()`
cannot be spread on the component next to the controller. Instead, create a component that accepts
the same props, passes the props that the controller supersedes to the hook and forwards the rest to
the component. The form binds to the props of that component, and the component owns the controller:

<Demo data={PinInputDemos.form} />

The pattern has three rules:

- Pass every prop that the `controller` prop supersedes to the hook, not only `value`,
  `defaultValue` and `onChange`. The `controller` prop description in the props table lists them.
  An option left on the component, for example `length` on `PinInput` or `format` on `TimePicker`,
  is ignored once a controller is set.
- Keep `error`, `onFocus` and `onBlur` on the component. They are not state props, so validation
  errors and touched/dirty tracking work the same way as without a controller.
- Use `mode: 'uncontrolled'` and set `key={form.key('field')}` on the component that calls the hook.
  In this mode `form.reset()` and `form.setFieldValue()` remount the field, and the controller with
  it. In `mode: 'controlled'`, the form can only change the `value` prop, and a partially entered
  time or date is reported as an empty value: it is the same before and after `form.reset()`, so
  the controller receives no change and the partial entry stays on screen.

Actions called on the controller inside the component, for example `clear()` or `setValue()`, report
through `onChange` the same way as typing, so the form stays in sync. `getValue()` and the last
`onChange` always agree: a value that the component cannot report, for example an incomplete time or
a `MaskedDateInput` date outside of `minDate`/`maxDate`, is an empty string or `null` for both.

The component that owns the controller is also the place to use queries that the form cannot see.
The form knows only that an incomplete time is empty, while `controller.hasValue()` knows that the
user has started typing:

<Demo data={TimePickerDemos.form} />

The same component works with other form libraries. With
[react-hook-form](https://react-hook-form.com/), pass the `field` props of `Controller`:

```tsx
import { Controller, useForm } from 'react-hook-form';

function Demo() {
  const { control, handleSubmit } = useForm({ defaultValues: { code: '' } });

  return (
    <form onSubmit={handleSubmit((values) => console.log(values))}>
      <Controller
        name="code"
        control={control}
        rules={{ minLength: 6 }}
        render={({ field, fieldState }) => (
          <PinField
            length={6}
            value={field.value}
            onChange={field.onChange}
            onBlur={field.onBlur}
            error={fieldState.error ? 'Enter all 6 digits' : null}
          />
        )}
      />
    </form>
  );
}
```

## Reading state

A controller is reactive: the component that called the hook re-renders when the state changes,
so you can read the state during render with query functions:

```tsx
import { Accordion, Button, Text, useAccordion } from '@mantine/core';

function Demo() {
  const controller = useAccordion({ multiple: true });
  const expanded = controller.getExpandedItems();

  return (
    <>
      <Text>{expanded.length} items expanded</Text>
      <Button disabled={expanded.length === 0} onClick={controller.collapseAll}>
        Collapse all
      </Button>
      <Accordion controller={controller}>{/* items */}</Accordion>
    </>
  );
}
```

Actions and queries keep the same identity for the lifetime of the controller, so they are safe as
`useEffect` and `useCallback` dependencies and as props of memoized components. Queries always
return the latest value, both during render and inside callbacks, where a value captured by a
closure would be stale:

```tsx
import { useEffect } from 'react';
import { useStepper } from '@mantine/core';

function Demo() {
  const controller = useStepper();

  useEffect(() => {
    const handler = (event: KeyboardEvent) => {
      if (event.key === 'ArrowRight') {
        controller.next();
      }
    };

    window.addEventListener('keydown', handler);
    return () => window.removeEventListener('keydown', handler);
  }, [controller.next]);

  return null;
}
```

Queries that depend on rendered children, for example `getItems()` on `Accordion` or
`getStepCount()` on `Stepper`, report what is mounted at the moment of the call and return an
empty result before the component is rendered. Stores give the same guarantees, except
`useDataGrid`, which returns a new object on every render.

## TypeScript

Controller and store types are named after the component and exported from the same package as
the hook. Use them to type a controller that is created in one component and passed to another:

```tsx
import { Accordion, useAccordion } from '@mantine/core';
import type { AccordionController, AccordionControllerOptions } from '@mantine/core';

interface SettingsAccordionProps {
  controller: AccordionController<true>;
}

function SettingsAccordion({ controller }: SettingsAccordionProps) {
  return <Accordion controller={controller}>{/* items */}</Accordion>;
}

function useSettingsAccordion(options: AccordionControllerOptions<true>) {
  return useAccordion({ ...options, multiple: true });
}

function Demo() {
  const controller = useSettingsAccordion({ defaultValue: ['profile'] });
  return <SettingsAccordion controller={controller} />;
}
```

When the state type depends on an option, the type is a generic that is inferred from the options
passed to the hook and flows through the `controller` prop to the component:

```tsx
import { useAccordion } from '@mantine/core';

const single = useAccordion();
single.getValue(); // -> string | null

const multiple = useAccordion({ multiple: true });
multiple.getValue(); // -> string[]
```
