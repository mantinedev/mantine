# 9.x → 10.x migration guide

## Update dependencies

Update all `@mantine/*` packages to version 10.x.

## Colors system changes

10.x has a new colors system. Most applications get the new look without code changes,
the cases that require changes are listed below.

### New OKLCH default palettes

All default colors were regenerated in the OKLCH color space. Color names and the number
of shades are the same, color values are different. The default `primaryShade` changed
from `{ light: 6, dark: 8 }` to `{ light: 6, dark: 7 }`.

### `--mantine-color-*` CSS variables are now OKLCH strings

In 9.x these variables had hex or RGB values. In 10.x their values are `oklch(L C H)` strings,
for example `oklch(0.52 0.22 255)`.

Changes are required if your application:

- Reads `--mantine-color-*` values from the DOM (for example, with `getComputedStyle`) and parses
  them as hex or RGB
- Passes CSS variable values to canvas `ctx.fillStyle` or other API that accepts only
  legacy color formats

In these cases, update the code to work with `oklch` values or use the [v9 opt-out](#v9-opt-out).

depending on the background color. The following components are affected:

```tsx
import { createTheme, MantineProvider } from '@mantine/core';

}
```

Or disable it on individual components:

```tsx
import { Button } from '@mantine/core';

function Demo() {
  return <Button autoContrast={false} color="yellow.3">Label</Button>;
}
```

### Paper is deprecated — use Surface

`Paper` is deprecated and will be removed in 11.0. It still works in 10.x without visual changes.
Replace it with [Surface](/core/surface), which supports the same props:

```tsx
import { Paper, Surface } from '@mantine/core';

// ❌ Deprecated
function Demo() {
  return <Paper shadow="sm" p="md">Content</Paper>;
}

// ✅ Use Surface instead
function Demo() {
  return <Surface shadow="sm" p="md">Content</Surface>;
}
```

In light color scheme `Surface` looks the same as `Paper`. In dark color scheme a standalone
`Surface` is one shade lighter than `Paper`, and each nested `Surface` is one level higher:

```tsx
import { Surface } from '@mantine/core';

// Automatic depth stepping – each nested Surface steps one level higher in dark mode
function Demo() {
  return (
    <Surface shadow="sm" p="md">
      <Surface p="md">
        One level deeper
      </Surface>
    </Surface>
  );
}
```

To keep the `Paper` appearance in dark color scheme, set `level={0}`,
see the [Surface documentation](/core/surface) for details.

### Darker dark theme

The dark color scheme is darker than in 9.x: the page background is approximately two steps
darker than the old `dark-7`. If you relied on specific `dark-N` values for backgrounds,
test your application in dark color scheme and adjust the styles.

Other changes in dark color scheme:

- `Popover`, `Menu`, `HoverCard` and `Combobox` based components (`Select`, `Autocomplete`, etc.)
  dropdowns have `dark-7` background instead of `dark-6`, the same as `Modal` and `Drawer`
- `SegmentedControl` root, `Tabs` `contained` list and `ScrollArea` scrollbars use
  the `--mantine-color-surface-sunken` variable (`dark-9`) instead of `dark-4`/`dark-6`
- `Code`, `Kbd`, `CodeHighlight`, `JsonViewer` and `Typography` code elements use
  the `--mantine-color-surface-muted` variable (`dark-5`)
- Focus rings use the new `--mantine-color-focus-ring` variable instead of
  `--mantine-primary-color-filled`. It is shade 5 of `theme.primaryColor` instead of
  `primaryShade.dark`. Light color scheme is not changed.

### New semantic color variables

Components now use semantic CSS variables instead of `gray-N` and `dark-N` colors.
Override them to change colors of all components:

```css
/* Example: custom border color */
[data-mantine-color-scheme='light'] {
  --mantine-color-border: #d0d0d0;
  --mantine-color-border-subtle: #e8e8e8;
}

[data-mantine-color-scheme='dark'] {
  --mantine-color-border: #404040;
  --mantine-color-border-subtle: #333;
}
```

The variables reference palette shades, so existing overrides of shades
(for example, `--mantine-color-gray-3`) continue to work.

### Customizing surfaces and the dark ramp

Use the `surfaces` theme key to change surface backgrounds for each color scheme:

```tsx
import { createTheme } from '@mantine/core';

const theme = createTheme({
  surfaces: {
    dark: {
      panel: '#101113',
    },
  },
});
```

Use the `tintColors` function to mix a color into every shade of a colors tuple.
Use it with `dark` colors only, tinting light neutral colors makes light surfaces darker:

```tsx
import { tintColors, darkColors, createTheme } from '@mantine/core';

const theme = createTheme({
  colors: {
    dark: tintColors(darkColors, '#5c7cfa', 0.15),
  },
});
```

`tintColors` returns `color-mix(in oklab, ...)` strings, not resolved color values. The result
cannot be passed to functions that expect a color value, for example `darken`.

### Warning and info color mappings

Built-in semantic colors are `error` and `success` only. For warning and info
states in `Alert`, `Notification` and similar components, use `yellow` and `blue` colors:

```tsx
import { Alert } from '@mantine/core';

function Demo() {
  return (
    <>
      <Alert color="yellow" title="Warning">
        This is a warning message.
      </Alert>
      <Alert color="blue" title="Info">
        This is an informational message.
      </Alert>
    </>
  );
}
```

## Disabled state

Disabled elements no longer have gray colors. Components keep their regular colors and are
displayed with reduced opacity. Use `theme.disabledOpacity` (`0.5` by default) to change it,
the value is available as `--mantine-disabled-opacity` CSS variable:

```tsx
import { createTheme, MantineProvider } from '@mantine/core';

const theme = createTheme({
  disabledOpacity: 0.4,
});

function Demo() {
  return <MantineProvider theme={theme}>{/* Your app */}</MantineProvider>;
}
```

The `--mantine-color-disabled`, `--mantine-color-disabled-color` and
`--mantine-color-disabled-border` CSS variables were removed. If you used them in your
styles, replace them with the opacity variable:

```css
.custom-control:disabled {
  opacity: var(--mantine-disabled-opacity);
}
```

The `disabledBody`, `disabledText` and `disabledBorder` keys of `vars.colors` in
`@mantine/vanilla-extract` were removed as well, use `--mantine-disabled-opacity`
in your `.css.ts` files instead.

Note that the [v9 opt-out](#v9-opt-out) does not restore the gray disabled styles.

## Blockquote changes

[Blockquote](/core/blockquote) has new styles:

- It no longer has a background and rounded corners. The `radius` prop and `--bq-bg-light`,
  `--bq-bg-dark`, `--bq-radius` CSS variables were removed.
- The icon is displayed above the quote instead of the top left corner
- The default `iconSize` is `24` instead of `48`

If you used the removed prop or variables, use the `root` selector in `styles` or `classNames` instead:

```tsx
import { Blockquote } from '@mantine/core';

function Demo() {
  return (
    <Blockquote
      styles={{
        root: {
          backgroundColor: 'var(--mantine-color-blue-light)',
          borderRadius: 'var(--mantine-radius-md)',
        },
      }}
    >
      Life is like an npm install – you never know what you are going to get.
    </Blockquote>
  );
}
```

## ColorPicker changes

[ColorPicker](/core/color-picker) and [ColorInput](/core/color-input) changes:

- `10` swatches per row are displayed by default instead of `7`. Set `swatchesPerRow={7}` to restore
  the previous value.
- Saturation picker, sliders and swatches use `theme.defaultRadius`. Use the new `radius` prop of
  `ColorPicker` to change it. `ColorInput` does not pass its `radius` prop to the picker.

## Slider changes

[Slider](/core/slider) and [RangeSlider](/core/range-slider) thumb has new styles:

- The thumb size depends on `size` prop (from 14px for `xs` to 26px for `xl`) instead of
  being twice the track height. Use `thumbSize` prop to restore the previous size.
- The thumb is white with a 2px colored border in both color schemes. Set `variant="filled"`
  to fill the thumb with the slider color.

If you changed `thumb` styles with Styles API, check that they still look as intended.

## Stepper.Step step, state, allowStepClick and onClick props

If you set `step`, `state`, `allowStepClick` or `onClick` on a `Stepper.Step` inside a
[Stepper](/core/stepper), remove them – `Stepper` ignored them in 9.x and applies them in 10.0:

```tsx
import { Stepper } from '@mantine/core';

function Demo() {
  return (
    <Stepper active={1}>
      {/* This step is now inactive and displays 6 as its icon */}
      <Stepper.Step label="First" step={5} state="stepInactive" />
      <Stepper.Step label="Second" />
    </Stepper>
  );
}
```

Keep them only on steps that should not follow the `active` prop of `Stepper`.

## Timeline data-opposite attribute

If your styles target `[data-opposite]` on the [Timeline](/core/timeline) root element, target the
opposite content instead – `Timeline` no longer sets the attribute:

```css
/* 9.x */
.timeline[data-opposite] {
  /* ... */
}

/* 10.0 */
.timeline:has(.mantine-Timeline-itemOpposite) {
  /* ... */
}
```

## Controller hook types renamed

Types of `useTimer`, `useEditable` and `useImageCropper` hooks were renamed. The old names
and the `useHook.Options`/`useHook.ReturnValue` namespace types were removed:

    ['`UseTimerOptions`', '`TimerControllerOptions`'],
    ['`UseTimerReturnValue`', '`TimerController`'],
    ['`UseEditableOptions`', '`EditableControllerOptions`'],
    ['`UseEditableReturnValue`', '`EditableController`'],

```tsx
import type { UseTimerReturnValue } from '@mantine/core';

// 10.x
import type { TimerController } from '@mantine/core';
```

## Tree store prop

The `tree` prop of `Tree` is renamed to `store`, and the `TreeController` type is renamed to `TreeStore`.
The `tree` field of the `renderNode` payload and the `tree` prop of `FlatTreeNode` are renamed
to `store` as well:

```tsx
// 9.x
import { Tree, useTree } from '@mantine/core';

function Demo() {
  const tree = useTree();
  return (
    <Tree
      data={data}
      tree={tree}
      renderNode={({ node, tree }) => (
        <div onClick={() => tree.toggleExpanded(node.value)}>{node.label}</div>
      )}
    />
  );
}

// 10.x
import { Tree, useTree } from '@mantine/core';

function Demo() {
  const store = useTree();
  return (
    <Tree
      data={data}
      store={store}
      renderNode={({ node, store }) => (
        <div onClick={() => store.toggleExpanded(node.value)}>{node.label}</div>
      )}
    />
  );
}
```

## Picker inputs calendar theme defaults

`defaultLevel` and `defaultDate` set in the theme `defaultProps` of `Calendar` and picker
components (`DatePicker`, `MonthPicker`, `YearPicker`, `WeekPicker`, `QuarterPicker`) no longer
apply to the dropdown of picker inputs (`DatePickerInput`, `MonthPickerInput`, etc.).
Set them on the input component instead:

```tsx
import { createTheme } from '@mantine/core';
import { DatePickerInput } from '@mantine/dates';

const theme = createTheme({
  components: {
    DatePickerInput: DatePickerInput.extend({
      defaultProps: { defaultLevel: 'year' },
    }),
  },
});
```

## Picker inputs popoverProps.opened

Picker inputs (`DatePickerInput`, `MonthPickerInput`, etc.) and `DateTimePicker` now call
`popoverProps.onChange` every time the dropdown is opened or closed. If you pass `popoverProps.opened`,
update it in `popoverProps.onChange`, otherwise the input cannot open or close its dropdown:

```tsx
import { useState } from 'react';
import { DatePickerInput } from '@mantine/dates';

function Demo() {
  const [opened, setOpened] = useState(false);
  return <DatePickerInput popoverProps={{ opened, onChange: setOpened }} />;
}
```

When you pass the `controller` prop, `popoverProps.opened` and `popoverProps.onChange` are ignored. Pass
`dropdownOpened` and `onDropdownOpenedChange` to the controller hook instead.

## Picker inputs dropdown type and submit button

Picker inputs (`DatePickerInput`, `MonthPickerInput`, etc.) and `DateTimePicker` now open
a bottom `Drawer` instead of a `Popover` when the viewport is narrower than `theme.breakpoints.sm`.
In `drawer` and `modal` dropdowns `onChange` is called only when the user presses the submit button.

- To use the popover on all viewports, set `dropdownType="popover"`
- To call `onChange` when a date is selected in the drawer or modal, set `applyOnSubmit={false}`

Both props can be set for all components in the theme:

```tsx
import { createTheme } from '@mantine/core';
import { DatePickerInput, DateTimePicker } from '@mantine/dates';

const theme = createTheme({
  components: {
    DatePickerInput: DatePickerInput.extend({
      defaultProps: { dropdownType: 'popover' },
    }),
    DateTimePicker: DateTimePicker.extend({
      defaultProps: { applyOnSubmit: false },
    }),
  },
});
```

`dropdownType` prop also accepts `'drawer'` and an object with breakpoints,
for example `{ base: 'drawer', sm: 'popover' }`.

## DateTimePicker and InlineDateTimePicker submit button

`DateTimePicker` and `InlineDateTimePicker` submit button is now a `Button` with a text label (`Save` by
default) instead of an `ActionIcon` with a check icon. `submitButtonProps` accepts `Button` props:
remove `ActionIcon` specific props, for example `size="input-sm"`. To change the label, use
`submitButtonLabel` prop or the `submitButtonLabel` setting of `DatesProvider`:

```tsx
import { DatesProvider, DateTimePicker } from '@mantine/dates';

function Demo() {
  return (
    <DatesProvider settings={{ submitButtonLabel: 'Apply' }}>
      <DateTimePicker submitButtonProps={{ variant: 'light' }} />
    </DatesProvider>
  );
}
```

## useMatches options argument

`useMatches` no longer accepts the second `options` argument (`getInitialValueInEffect`).
The hook returns the `base` value on the server and during hydration. Remove the second argument:

```tsx
import { useMatches } from '@mantine/core';

// Before
const value = useMatches({ base: 'a', sm: 'b' }, { getInitialValueInEffect: false });

// After
const value = useMatches({ base: 'a', sm: 'b' });
```

## TimeInput data-empty attribute

`TimeInput` now sets the `data-empty` attribute on the input element while it has no value. If you
use `data-empty` on `TimeInput` for your own purposes, rename your attribute.

## Combobox store listId and selectedOptionIndex

The `listId` and `selectedOptionIndex` fields are removed from the store returned by `useCombobox` and
`useVirtualizedCombobox`. Use `getListId()` and `getSelectedOptionIndex()` functions instead:

```tsx
const combobox = useCombobox();

// 9.x
combobox.listId;
combobox.selectedOptionIndex;

// 10.x
combobox.getListId();
combobox.getSelectedOptionIndex();
```

`useVirtualizedCombobox` still accepts the `selectedOptionIndex` option.

## comboboxProps.store in Select, MultiSelect, TagsInput and Autocomplete

`Select`, `MultiSelect`, `TagsInput` and `Autocomplete` ignore `store` passed in `comboboxProps`.
To control the dropdown, create a store with the component hook (`useSelect`, `useMultiSelect`,
`useTagsInput` or `useAutocomplete`) and pass it to the `store` prop. It includes all `useCombobox` actions:

```tsx
// 9.x
const combobox = useCombobox();
<MultiSelect data={data} comboboxProps={{ store: combobox }} />;

// 10.x
const store = useMultiSelect();
<MultiSelect data={data} store={store} />;
```

## Controller hooks return a memoized object

`useTimer`, `useEditable`, `useImageCropper` and `usePagination` returned a new object on every
render in 9.x. In 10.x the returned object changes only when the state changes, and its actions
keep the same reference.

If you use the returned object as a `useEffect` or `useCallback` dependency, the effect now runs
less often. Depend on individual actions or on state values instead:

```tsx
const controller = useTimer();

// Ran on every render in 9.x, runs only when the timer state changes in 10.x
useEffect(() => {
  /* ... */
}, [controller]);

// Use this instead
const running = controller.isRunning();

useEffect(() => {
  /* ... */
}, [running]);
```

`ModalBase*` and `NativeScrollArea` components and their props types are no longer exported from
`@mantine/core`. If you built a custom dialog with them,
use [Modal](/core/modal#compound-components) or [Drawer](/core/drawer#compound-components)
compound components instead:

## Drawer swipe to dismiss

[Drawer](/core/drawer#swipe-to-dismiss) can now be closed with a swipe gesture, it is enabled
by default. To disable it, set `withSwipe={false}` on `Drawer` or in the theme:

```tsx
import { createTheme, Drawer } from '@mantine/core';

const theme = createTheme({
  components: {
    Drawer: Drawer.extend({
      defaultProps: { withSwipe: false },
    }),
  },
});
```

To disable the swipe gesture only for some elements inside the drawer (for example, drag and drop
lists), set the `data-drawer-no-swipe` attribute on these elements:

```tsx
import { Drawer } from '@mantine/core';

function Demo() {
  return (
    <Drawer opened onClose={() => {}}>
      <div data-drawer-no-swipe>{/* Draggable content */}</div>
    </Drawer>
  );
}
```

## Uncontrolled mode is the default

`useForm` and `useField` now use `mode: 'uncontrolled'` by default. In uncontrolled mode the
component does not rerender when the user types and `form.values` is a snapshot from the last
render. If a form reads `form.values` during render, either replace `form.values` with
`form.getValues()` in event handlers and `form.useWatchValue('path')` in render, or set
`mode: 'controlled'` to keep the previous behavior:

```tsx
// 9.x
const form = useForm({ initialValues: { name: '' } });
<Text>{form.values.name}</Text>

// 10.x
const form = useForm({ mode: 'controlled', initialValues: { name: '' } });
<Text>{form.values.name}</Text>

// 10.x, uncontrolled
const form = useForm({ initialValues: { name: '' } });
const name = form.useWatchValue('name');
<Text>{name}</Text>
```

See [form modes](/form/uncontrolled) for the differences between the two modes.

## form.key removed

Remove `key={form.key('path')}` from inputs rendered with `form.getInputProps`. Inputs now
receive values from `form.setFieldValue`, `form.setValues` and `form.reset` without a remount.
In lists, use a stable key of the list item, for example a `randomId()` stored in the item,
not the field path:

```tsx
// 9.x
<TextInput key={form.key('name')} {...form.getInputProps('name')} />

// 10.x
<TextInput {...form.getInputProps('name')} />
```

`useField` no longer returns `key`, remove `key={field.key}` the same way. The `Key` type is no longer exported, remove its imports.

## Uncontrolled form inputs receive value

In `mode: 'uncontrolled'`, `form.getInputProps` and `field.getInputProps` return `value` and
`checked` instead of `defaultValue` and `defaultChecked`, the same as in controlled mode. Change
custom inputs that read only `defaultValue` to read `value`, and `enhanceGetInputProps`
functions that read `inputProps.defaultValue` to read `inputProps.value`.

Set an initial value for every field that is rendered with an input. A field that is missing
from `initialValues` is passed as `value={undefined}` and React warns when it later becomes
controlled, as it did in controlled mode before.

If your custom input keeps state that `value` cannot express, for example a partially entered
date, use the [use-form-field](/hooks/use-form-field#onexternalwrite) hook to clear it when
the form writes the value. Previously the `key` remount did that.

## form.isDirty and form.isTouched in uncontrolled mode

In `mode: 'uncontrolled'`, the form component no longer rerenders when a field becomes dirty or
clean. If you read `form.isDirty()` or `form.isTouched()` during render, for example to disable a
submit button, replace the call with the `form.useDirty()` or `form.useTouched()` hook, both accept
an optional field path:

```tsx
// 9.x
<Button disabled={!form.isDirty()}>Save</Button>

// 10.x
const dirty = form.useDirty();
<Button disabled={!dirty}>Save</Button>
```

Calls outside of render, for example in `form.onSubmit` or event handlers, do not change.

## Form values are not cloned on every change

`form.getValues()` and `form.values` keep the same object references for values that did not
change. Do not mutate the returned object, use `form.setFieldValue` or `form.setValues` instead.

## form.setValues clears only errors of changed fields

`form.setValues` now clears errors only of the fields it sets and their nested fields, other
errors stay. If you load data with `form.setValues` after a failed submit and expect all errors
to disappear, call `form.clearErrors()` before it:

```tsx
// 9.x
form.setValues(data);

// 10.x
form.clearErrors();
form.setValues(data);
```

## UseFieldReturnType type parameters

`UseFieldReturnType` accepts two type parameters instead of three, remove the third `Mode`
argument: `UseFieldReturnType<string, 'input', 'uncontrolled'>` becomes
`UseFieldReturnType<string, 'input'>`.

## v9 opt-out

If your application cannot be migrated immediately, restore 9.x colors, variants
and `autoContrast: false` with `v9Theme` and `v9CssVariablesResolver`:

```tsx
import {
  MantineProvider,
  v9Theme,
  v9CssVariablesResolver,
} from '@mantine/core';

function App() {
  return (
    <MantineProvider
      theme={v9Theme}
      cssVariablesResolver={v9CssVariablesResolver}
    >
      {/* Your app */}
    </MantineProvider>
  );
}
```

`v9Theme` contains 9.x hex colors and sets `autoContrast: false`.
`v9CssVariablesResolver` outputs CSS variables as hex/RGB values. Both are temporary
and will be removed in 11.0.

## Browser support

The OKLCH color format and `color-mix()` function used for variant derivations require the
following minimum browser versions:

- Chrome/Edge 111+ (released March 2023)
- Safari 16.2+ (released December 2022)
- Firefox 113+ (released May 2023)

To support older browsers, use the [v9 opt-out](#v9-opt-out) or configure
a PostCSS plugin that converts `oklch` values.
